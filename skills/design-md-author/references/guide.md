## 引言

### 传统设计系统的痛点

在多团队、多 Agent 协作的当下，常见的设计系统问题：

| 痛点 | 传统做法 | 后果 |
|------|---------|------|
| 多项目共用一套设计 | 每个项目重写一遍按钮/表格 | 视觉不一致、维护成本高 |
| AI Agent 生成代码 | Agent 自由发挥、随机选型 | 可能选 `el-button` 而非项目封装的 `DsButton` |
| 颜色硬编码 | `color: #XXXXXX` 散落各文件 | 改主题时全局搜索替换，容易遗漏 |
| 设计稿与实现脱节 | 各凭理解 | 反复来回沟通、视觉评审会爆炸 |
| 文档分散 | README + Storybook + Figma + Wiki | 找不到一份"权威真源" |

### 传统方案为什么不够？

- **Storybook** 是组件预览站（看），不是选型依据（决策）
- **README** 是入门指南（学），不能约束 Agent（管）
- **Figma** 是设计稿（看），无法直接驱动开发（用）
- **设计文档长文** 是给人读的（慢），不是给 AI 读的（机读）

### DESIGN.md 的定位

> **一份给 AI 看的设计系统合同（Single Source of Truth）**

它把所有"组件、令牌、模板、约束"集中到**一份文件**里，让：

- **dev Agent** 生成业务页时**不靠预览站**也能开工
- **product/design Agent** 生成原型时**遵守同一套视觉约束**
- **新人** 接手项目时**只看一份**就能落地

### 适用场景判断

| 信号 | 需要写 | 不必写 |
|------|--------|--------|
| 团队规模 | 多人/多 Agent 协作 | 单人小工具 |
| 项目复用 | 多个宿主项目共用一套设计 | 单项目独立 |
| AI 协作深度 | Agent 频繁生成新页面 | 纯手写 |
| 视觉一致性痛点 | 反复出现"和稿子不一致" | 设计稿已死，纯维护期 |

## 核心理念

### SSOT（Single Source of Truth）三大原则

#### 原则 1：单一来源
设计规则**只写一次**。任何变更都先改这一份，再同步到代码/文档。

#### 原则 2：可机读
Agent 直接消费，不需要人解读。所以用：
- YAML frontmatter（机器可读元数据）
- 表格（结构化对齐）
- CSS 变量名（与 `tokens.css` 字符级一致）
- 显式 ✅ / ❌（禁止项一目了然）

#### 原则 3：决策完整
看完就知道**怎么做**，不用问别人。所以必须包含：
- 选型规则（用哪个组件）
- 缺口回退（没有就用什么）
- 禁用清单（什么绝对不能用）
- 已知偏差（设计稿与实现的差距）

### DESIGN.md 不是什么

| 误解 | 真相 |
|------|------|
| ❌ 给人读的设计手册 | ✅ `audience: agent`，是 Agent 工作守则 |
| ❌ 组件 API 文档 | ✅ API 摘要附录 A，详细看 Storybook |
| ❌ 风格指南长文 | ✅ 风格约束是数值表，不写散文 |
| ❌ 能替代 AGENTS.md | ✅ 工程规范在 AGENTS，设计规范在 DESIGN，**职责分离** |
| ❌ 写完一次就不动 | ✅ 改组件必须同步更新（附录 A + 映射表 + 附录 B） |

### 与其他文档的边界

```
DESIGN.md       → 设计系统 SSOT（设计/选型/令牌）
AGENTS.md       → 工程 SSOT（包管理/Node/命令/目录）
README.md       → 安装与使用入门
Storybook       → 视觉预览 + 代码面板
CHANGELOG.md    → 变更历史
```

**写 DESIGN.md 时不要重复**：
- ❌ npm 包安装步骤（AGENTS.md 已有）
- ❌ 完整组件 props 文档（Storybook 已有）
- ❌ 业务功能说明（README 已有）
- ❌ 提交规范（AGENTS.md 已有）

## 四层模型

### DESIGN.md 的核心原则

| 层级 | 是什么 | Agent 含义 |
|------|--------|------------|
| **L0 设计 SSOT** | 本文（DESIGN.md） | 选型、令牌、布局、模板（**核心，不依赖任何库**） |
| **L1 组件库（可选增强）** | `@your-org/ui` + tokens | 有则优先使用，生成质量更佳；无则按令牌+框架原语代码实现 |
| **参照层（可选）** | Storybook 预览 + 代码面板 | 核对视觉态与外观；不替代 L0 |
| **L2 框架原语** | Element Plus / Ant Design 等 | 无组件库时的基础控件来源 |
| **禁止层** | 第三 UI 库 / 自研同款 / 硬编码色 | 任何角色禁止 |

### 关键设计

- **L0 是真源**：不能复制成第二份。所有 Agent 生成代码必须读它。**即使没有组件库，仅凭 L0 也能生成**。
- **L1 是可选增强**：有组件库时优先使用，生成结果更一致；没有时按令牌 + 框架原语组合代码实现。
- **参照层仅作视觉参照**：缺网/无仓时，Agent 仍可仅凭本文生成。
- **L2 是基础控件来源**：无组件库时直接用框架原语，有组件库时仅作缺口补充。

### 组件选型决策规则（核心中的核心）

```text
1. 查附录 A 是否有项目封装组件等价
2. 有组件库 → 优先使用封装组件；禁止框架原语同款、禁止业务换皮包装
3. 无组件库 → 直接用框架原语（Element Plus/Ant Design 等）+ 附录 B 令牌约束视觉
4. 框架原语也无 → 最小 DOM + 附录 B 令牌
5. 禁止：第三库 / 自研同款 / 硬编码色
```

| 角色 | 目标 | 入口 |

| **dev** | 目标A（设计稿还原业务页） | 主流程章节 + 附录 A/B/C |
| **product** | 目标B（原型/演示） | 附录 G + D/E/F + 页面模板 |
| **design** | 目标B（视觉对齐） | 附录 G + 视觉规范章节 |
| **author** | 目标C（从 0 写设计系统） | 本文（指南）+ 7 步法 + Step 0 + 自检清单 |

### 三大目标

| # | 角色 | 输入 | 输出 |
|---|------|------|------|
| **目标A** | dev | 设计稿 + 本文 | 宿主业务页（令牌 + 组件） |

## 9 大模块

一个成熟设计系统的成功在于它有**完整的 9 大模块**。新项目复用时建议按需裁剪，但骨架一致。

### 模块 1：YAML Frontmatter（机器可读元数据）

```yaml
---
name: [项目] Design System
description: [一句话说明] · Agent 契约
audience: agent
version: 0.1.0                    # 语义化版本；初版从 0.1.0 起步，破坏性变更递增主版本位并记 CHANGELOG
framework: vue@3 | vue@2 | react
componentLibrary: element-plus@2.4.4 | element-ui@2.15 | antd
package: "@your-org/ui"           # 业务包名（无组件库时省略本行）
preview: [预览站地址，可选]
updated: 2026-08-23
status: Draft | Active
---
```

**关键字段**：
- `audience: agent` 明确文件是给 Agent 看的
- `framework` + `componentLibrary` 锁定技术栈（无组件库时只写 framework）
- `updated` 强制维护时更新日期；令牌/选型变更同步递增 `version`

### 模块 2：顶层原则（4 层模型 + 组件选型决策规则）

最重要的一页纸。模板：

```markdown
## 顶层原则

| 层级 | 是什么 | Agent 含义 |
|------|--------|------------|
| L0 设计 SSOT | 本文件 | 选型、令牌、布局（核心，不依赖任何库） |
| L1 组件库（可选） | @your-org/ui | 有则优先使用，生成质量更佳 |
| L2 框架原语 | [框架原语] | 无组件库时的基础控件来源 |
| 禁止层 | 第三库/硬编码 | 任何角色禁止 |

**组件选型决策规则**：
1. 查附录 A 有封装组件 → 优先使用；禁止同款原语替代
2. 无组件库 → 框架原语 + 附录 B 令牌约束视觉
3. 全无 → 最小 DOM + 附录 B 令牌；禁止第三库
```

### 模块 3：目标对齐（两类目标 + 角色路由）

定义两类目标 + 三角色路由：

```markdown
## 目标（全体 Agent 必须对齐）

| # | 角色 | 输入 | 输出 |
|---|------|------|------|
| 目标A | dev | 设计稿 + 本文 | 宿主业务页 |
| 目标B | product/design | 本文 + 必要 PRD | 原型/演示 |
```

### 模块 4：dev 代码实现流程（主流程章节）

从设计稿到代码的决策顺序 + 页面模板。

**决策顺序**：
```
1. 页面模板（选模板）
2. 场景→组件（附录 A）
3. 缺口 → 附录 C（框架原语白名单）
4. 配色间距 → 附录 B
5. 态：loading / empty / error / disabled
6. （推荐）Storybook 核对各状态
7. 业务逻辑
```

**页面模板**（最少 4 类）：

| 模板 | 用途 | 组件链 |
|------|------|--------|
| **A 标准列表** | 绝大多数业务页 | 筛选表单 → 操作栏 → 数据表格 |
| **B 弹窗表单** | 新建/编辑 | Dialog + 字段 |
| **C 详情页** | 查看单个 | 标题 + Tag/Avatar/Steps |
| **D 结果反馈** | 提交成功/失败 | Result / Toast / Alert |

**交付自检清单**（必须有）：
```
- [ ] 有组件库时用封装组件；无组件库时用框架原语 + 令牌约束
- [ ] 附录 A 选型；有封装组件未用原语同款
- [ ] 视觉符合附录 B 令牌；无硬编码色
- [ ] 异步 loading；空态有占位
- [ ] 桌面 1440 宽验收
```

### 模块 5：设计令牌系统（附录 B）

#### 令牌三层模型（附录 B 的设计前提）

令牌不是扁平清单。扁平清单在超过 50 个后会命名混乱，且天然无法支撑暗色模式/多主题，必须按三层组织：

| 层 | 职责 | 命名示例 | 变更频率 |
|------|------|----------|----------|
| **primitive（原始值）** | 只定义数值色板，不承载语义 | `--blue-500`、`--gray-100` | 几乎不变 |
| **semantic（语义别名）** | 定义"什么用途用什么"，是**唯一换肤层** | `--colors-brand-primary: var(--blue-500)` | 换肤/暗色模式时才改 |
| **component（组件级）** | 特定组件的局部覆盖，opt-in | `--button-bg: var(--colors-brand-primary)` | 随业务增长 |

**规则**：
- ✅ 业务代码只允许引用 semantic 层；禁止直接引用 primitive 层
- ✅ 暗色模式/多品牌 = 只覆盖 semantic 层；primitive 与 component 层不动
- ❌ 禁止在 semantic 层硬编码数值：`--colors-brand-primary: var(--blue-600)` ✅；`--colors-brand-primary: #1677ff` ❌
- ❌ 禁止每来一个新组件就新增 primitive；先查现有 semantic 层能否覆盖

> **起步形态（合并层）**：MVP 阶段允许 primitive 与 semantic 合并为一层——令牌直接持值（如 `--colors-brand-primary: #主品牌色`），此时"禁止硬编码"规则暂缓，但必须在附录 B 标注"合并层，待拆层"；令牌超过 50 个或引入暗色模式前必须拆齐三层，拆层后禁止硬编码规则即时生效。下文 MVP 模板即"合并层"的起步形态。

**基础 4 组（必须有）+ 推荐 2 组（按需扩充）**：

| 组 | 级别 | 数量参考 | 示例 |
|----|------|---------|------|
| **颜色** | 基础 | 30–60 个 | 主品牌 / Hover / Active / 语义 / 状态 / 图表 |
| **间距** | 基础 | 6–10 级 | xs(4) sm(8) base(12) lg(16) xl(24) 2xl(32) 3xl(48) |
| **圆角** | 基础 | 4–6 个 | none/small(2) base(4) large(8) round(20) full(9999) |
| **字号** | 基础 | 5–8 个 | xs(12) sm(13) base(14) lg(16) xl(18) 2xl(20) |
| 阴影 | 推荐 | 3–4 个 | light / base / heavy / hover |
| 动效 | 推荐 | 2–3 个 | color(150ms) / shadow(200ms) |

## 7 步法

### Step 0：输入收集与决策权边界（Agent 执行必做）

开写前先分清哪些输入必须由用户拍板，哪些 Agent 可自行决定。**必问项未获答复时停下来问，禁止静默编造**——编造一份"看起来权威、实际全是幻觉决策"的 DESIGN.md，比不写更危险。

**必问项表**（右列 = 用户明确表示答不上 / "用默认值"时才采用的默认答案）：

| 必问项（决策权在人） | 新人默认答案（用户答不上时才用） |
|------------------------|-------------------------------|
| 框架与 UI 库确认 | 从仓库 package.json 推断；推断不出必须停下来问（此项无默认值） |
| 品牌色 / 主题风格来源 | 库默认主色起步，记入"已知偏差"，有设计稿后升级 |
| 业务域与页面类型假设 | 按中后台假设：A 标准列表 + B 弹窗表单为主体 |
| 团队规模与项目寿命 | 按单文件 MVP（200 行）；超 1000 行再按文件骨架决策表拆分 |
| 是否需要暗色模式 / 多主题 | 暂不需要；后续需要时按模块 5 拆齐令牌三层 |
| 组件库是否列入规划 | 不列入：附录 A 全 ❌ / 🔵，附录 C 作临时主注册表（见 Step 4 零期特则） |

**Agent 可自行决定**：令牌粒度与分组方式、表格格式、章节裁剪、MVP 组件短名单裁剪、附录 E / F / G 取舍、附录编号与排版。

> 执行规则：Agent 在开始时**一次性批量提问**全部必问项（避免反复打断），并把用户答复记入 frontmatter 备注或附录；提问前不动笔。用户答"不知道 / 用默认"＝采用右列默认答案，且**每条默认决策必须自动记入"已知偏差"**，保证可追溯、可升级。

### Step 1：确定读者与目标

回答三个问题：
1. **谁会用**？— dev / product / design / 全员
2. **解决什么问题**？— 多项目复用 / AI 协作 / 视觉一致性
3. **写多大**？— MVP（200 行）/ 完整（1000+ 行）

### Step 2：写顶层原则（最重要的一页纸）

复用本文"模块 2"模板。这一页纸**决定文档大部分价值**。

### Step 3：定义令牌系统（附录 B + tokens.css）

按"模块 5"的基础 4 组起步：
- 颜色（30 个）
- 间距（6 级）
- 圆角（4 个）
- 字号（5 个）

**文档之外必须同步产出代码交付物**（三者缺一，附录 B 就是纸面草案）：

```text
1. tokens.css —— 令牌实体，手写或 Style Dictionary 生成（见实战补充 3）
2. 注入项目入口 —— main.js/main.ts 或全局样式引入 tokens.css
3. 覆盖库主题 —— 用令牌映射覆盖 --el-* 等库变量（见实战补充 3）
4. 挂校验脚本 —— 从第一天起让防漂移闭环可执行（见「防漂移闭环」）
```

**占位符规范**（品牌色等用户未拍板的值）：
- 文档附录 B 统一写中文占位（如 `#主品牌色`），保持可读性；占位符不是合法 CSS 值，禁止直接抄进 tokens.css；
- tokens.css 一律先用**库默认值**作为实际值，行尾注释标记：`/* TODO(决策): 主品牌色，现用库默认 */`；
- Agent 规则：占位符要么向用户确认，要么用库默认值起步并记入"已知偏差"；**擅自编造具体色值属越界**。

### Step 4：写组件注册表（附录 A）

按"模块 7"模板，**先列基础组件，再列复合组件**。

**关键**：
- ✅ 标记可用
- 🔵 标记计划中，附临时回退（附录 C 原语）
- ❌ 标记未实现，并给出替代方案
- 每个组件标注"基于"哪个原语
- **MVP 封装短名单**（按四类页面模板的使用频次排序）：Button / Input / Select / Table / Dialog / Tag 六个优先封装；低频组件（Upload / Tree / ColorPicker 等）先标"❌ 未实现 + 替代方案"，有真实需求再封装；
- **零期特则**：从 0 起步时无任何封装组件，附录 A 全部为 🔵 / ❌，此时**附录 C 就是临时主注册表**；选型规则照常运转（查附录 A → 全不命中 → 走附录 C），不因注册表未就绪而失效

### Step 5：写组件-令牌映射表（注意两个方向）

按"模块 6"模板，**先写 3–5 个核心组件**：
- Button（最重要）
- Input / Select
- Dialog / Toast
- Tag / Avatar

> **两个方向，语义相反，别搞混**：存量库是"提取先行"——从已实现组件反向提取，映射表 = 现状快照；从 0 起步是"规格先行"——先写映射表作为组件实现目标，映射表 = 设计规格，实现组件时逐行对齐；实现后与规格不一致的，按实际改规格并记入已知偏差。

### Step 6：写页面模板

按"模块 4"的 4 类模板，基于**自己项目真实页面**归纳，不要照抄别人的。

**新项目还没有真实页面时（冷启动做法）**：

```text
1. 从"业务域假设"出发列 v0 模板：列出业务最可能出现的 5 类页面以内
   （中后台大概率是 A 标准列表 + B 弹窗表单占主体）
2. 用模块 4 骨架的组件链占位，不要发明新模板类型
3. 前 3 个真实页面落地后逐个校准模板：命中则保留，不命中则修订组件链
4. 模板随项目版本化：v0（假设）→ v1（3 页校准后）→ 稳定版
```

> 冷启动红线：不要为了"有"而发明第 5 类模板；四类已覆盖绝大多数中后台场景，模板库只在真实页面无法归入时才扩充。

### Step 7：写演示脚手架与数据契约（可选）

如果产品要演示站，加附录 E（脚手架）+ 附录 F（数据契约）。

### 完成标准：怎么判断"从 0 建成了"

不看行数，看四条可执行判断，全部命中才算建成：

| # | 验收项 | 做法 |
|---|--------|------|
| 1 | **真实页面走通** | 选 1 个真实页面按 Step 6 模板实现，交付自检清单逐项通过 |
| 2 | **令牌可解析** | DevTools 中附录 B 每个变量都能解析出值，无失效引用 |
| 3 | **防漂移可执行** | 校验脚本在当前仓库跑通且通过（文档与 tokens.css 一致） |
| 4 | **Agent 可发现** | 新会话的 Agent 只凭 AGENTS.md 的引用即可找到并消费 DESIGN.md |

> 初版发布评审门禁：四条验收全部命中后，由设计 + 前端负责人共同确认，方可把 frontmatter 从 `status: Draft` 升为 `Active`；在此之前，初版一律按"待校准假设"对待。

### DESIGN.md 自检清单（元校验）

验收"文档自身"的质量，与验收页面的交付自检清单相对；Author Agent 交付前逐项自查并输出结果：
- [ ] YAML frontmatter 完整（含 version / updated / status）；
- [ ] 附录 B 每个令牌要么有值、要么符合占位符规范；
- [ ] 附录 A 每个 ❌ / 🔵 都有替代方案 / 临时回退，无裸引用风险；

## 实战补充

> 本章回答新人最常问的问题：**“我用的不是同一个 UI 库，怎么把 DESIGN.md 适配过去？”**
> 骨架（结构/概念/模板）可直接复用；以下是需要自己摸索的“血肉”部分。

### 补充 1：不同 UI 库的主题覆盖方式对照（P0）

DESIGN.md 的令牌最终要“落”到组件库的主题机制上。不同库的覆盖方式完全不同：

| UI 库 | 主题机制 | 覆盖方式 | 在 DESIGN.md 中的写法 |
|-------|---------|---------|---------------------|
| **Element Plus** | CSS Variables（`--el-*`） | `:root { --el-color-primary: var(--brand-primary) }` | 附录 B 直接写 CSS 变量 |
| **Ant Design Vue 4.x** | CSS-in-JS token | `<ConfigProvider :theme="{ token: { colorPrimary } }">` | 附录 B 需标注 token 名映射 |
| **Naive UI** | JS 主题对象 | `n-config-provider` + `themeOverrides` | 附录 B 标注 overrides 路径 |
| **Arco Design Vue** | CSS Variables（`--arcoblue-*`） | 覆盖 `--arcoblue-6` 等 | 同 Element Plus |
| **Vant**（移动端） | CSS Variables（`--van-*`） | 覆盖 `--van-primary-color` | 同 Element Plus |
| **Element UI**（Vue 2） | SCSS 变量 | 换肤工具 / SCSS 变量覆盖 | 附录 B 需写 SCSS 变量名 |

**关键结论**：
- 基于 CSS Variables 的库（Element Plus / Arco / Vant）适配最简单，附录 B 可直接消费
- CSS-in-JS 的库（Ant Design / Naive UI）需要在附录 B 额外标注“令牌 → theme token”的映射关系
- 换库时，**附录 B 的语义名不变，只换“库变量映射列”**

### 补充 2：审计一个库并建立组件白名单的 5 步（P0）

换库后附录 A（组件注册表）和附录 C（原语白名单）需要重建：

```text
Step 1 盘点场景：列出项目需要的页面类型与控件（参考四类页面模板）
Step 2 对照库清单：打开目标库官方文档的组件列表，逐个对照
Step 3 三分类：
   ├─ 直接用：库组件满足需求，附录 C 登记
   ├─ 需封装：库组件能用但要统一视觉，规划封装组件进附录 A
   └─ 没有：库无此组件，记录缺口（最小 DOM + 令牌）
Step 4 填表：附录 A 写封装组件（含 ✅ 可用 / ❌ 未实现），附录 C 写原语白名单
Step 5 定回退：每个未实现组件必须写明替代方案
```

**经验参考**：一个中后台项目通常需审计几十个控件，其中大部分直接用、少部分需封装、个别是缺口。

### 补充 3：令牌的生成与注入流程（P0）

文章说“用 `var(--brand-primary)`”，但这些变量从哪来、怎么进项目？

#### 令牌来源（三选一）

| 来源 | 适用场景 | 做法 |
|------|---------|------|
| 设计稿提取 | 有 Figma/Sketch 稿 | 从设计稿的样式面板导出颜色/字号/间距 |
| 库默认主题起步 | 无设计稿 | 直接用目标库的默认色板作为初值 |
| 存量页面提取 | 旧项目 | DevTools 统计页面中高频使用的色值，归纳收敛 |

#### 生成 CSS 变量（三种方式）

```text
方式 A 手写 CSS（最简单，MVP 推荐）
   tokens.css 里直接写 :root { --brand-primary: ...; }

方式 B Style Dictionary（多端/多格式输出）
   JSON 源 → 构建 → tokens.css / tokens.scss / tokens.ts

方式 C SCSS 变量（Vue 2 / 旧项目）
   variables.scss → 编译时注入，但运行时不可换肤
```

#### 注入与对齐库主题（关键一步）

```css
/* 1. 定义自己的令牌 */
:root {
  --brand-primary: #主品牌色;
}

/* 2. 用令牌覆盖库变量（以 Element Plus 为例） */
:root {
  --el-color-primary: var(--brand-primary);
  --el-color-primary-light-3: var(--brand-hover);
}
```

**原则：自己的令牌是真源，库变量只是令牌的“消费方”**。这样附录 B 只维护一套语义名。

### 补充 4：组件-令牌映射表怎么查（P1）

拿到一个组件，怎么知道它用了哪些变量？三条路径：

| 路径 | 做法 | 适用 |
|------|------|------|
| **文档法** | 查库文档的“主题定制/Theming”章节，找组件相关变量清单 | 首选，最快 |
| **源码法** | 在库的源码/样式文件中搜 `var(--` 或组件名，看它引用了哪些变量 | 文档不全时 |
| **DevTools 法** | 页面审查元素 → Computed 面板 → 看实际生效的变量与值 | 运行时验证 |

**实操建议**：先用文档法建初稿，再用 DevTools 法逐个验证关键组件（Button / Input / Dialog 优先）。

### 补充 5：验证方法——怎么确认 Agent 真的遵守了（P1）

| 手段 | 做法 | 拦截什么 |
|------|------|---------|
| **stylelint 规则** | 禁用裸色值（如 `declaration-property-value-disallowed-list`） | 硬编码颜色 |
| **import 检查** | ESLint `no-restricted-imports` 禁止直接引被封装的原语组件 | 绕过封装组件 |
| **人工审查清单** | 用交付自检清单逐项过 | 结构性问题 |
| **视觉回归** | 截图对比（Playwright / Percy） | 视觉偏差 |
| **Agent 自检提示** | 生成后要求 Agent 对照交付清单逐项自查并输出结果 | 低级别错误 |

**优先级**：先上 stylelint + 人工清单（成本低）；项目稳定后再上视觉回归。

### 补充 6：存量项目渐进式采用（P2）

不要试图一次性迁移全部页面，分四阶段：

```text
阶段 1：写 MVP DESIGN.md（200 行）+ 令牌 CSS
阶段 2：新页面全部按 DESIGN.md 写（增量约束）
阶段 3：老页面按“改到就顺手迁”策略增量迁移，不专项重构
阶段 4：上 CI 拦截（stylelint/ESLint），固化规范
```

**红线**：不为了迁移而迁移；老页面没有需求变更时不动。

### 补充 7：没有设计稿时怎么定义令牌（P2）

```text
1. 用目标库默认主题起步（如 Element Plus 默认蓝）
2. 从存量页面提取高频色值，收敛到 10 个以内语义色
3. 间距/圆角/字号直接采用库默认值，先不自创
4. 附录 B 先写“当前值”，后续有设计稿时再升级，同步记入“已知偏差”章节
```

### 补充 8：多人协作约定（P2）

| 约定 | 说明 |
|------|------|
| **指定 owner** | DESIGN.md 有唯一维护责任人，避免无人管 |
| **同一 PR 同步** | 改组件代码 + 改 DESIGN.md 必须在同一个 PR，防止脱节 |
| **编号不可变** | 章节编号一旦发布不重排，只追加，避免外部引用失效 |
| **变更评审** | 令牌/选型规则变更需设计+前端双方评审 |
| **冲突仲裁** | 组件与本文冲突时：以本文为准，代码开 issue 修，写入“已知偏差”章节 |

### 已知偏差的处理

### 令牌破坏性变更的退场机制

"编号不可变"只保护章节编号；令牌重命名/删除对所有宿主项目同样是破坏性变更，必须有退场机制。

**规则**：
- ❌ 禁止静默改名/删除：直接把 `--brand-primary` 改成 `--colors-brand-primary` = 全体宿主破坏性变更
- ✅ 变更必须走四步退场流程：

```text
1. 标记：附录 B 中旧令牌标注"❌ 已废弃"+ 替代名 + 移除版本
2. 双名并存：tokens.css 中新旧名同时定义（旧名指向新值），过渡期不少于 1 个 minor 版本
3. 迁移：给出宿主迁移清单（全局搜索替换命令），宿主逐个迁移并销项
4. 移除：过渡期结束删除旧名，同步记入 CHANGELOG
```

**附录 B 废弃标记示例**：

| CSS 变量 | 值 | 状态 |
|---|---|---|
| `--brand-primary` | var(--colors-brand-primary) | ❌ 已废弃，v2.1 移除，改用 `--colors-brand-primary` |
| `--colors-brand-primary` | var(--blue-600) | ✅ 当前 |

## 防漂移闭环

### SSOT 最常见的死法：静默腐化

一份 1000 行的 DESIGN.md，最大的危险不是初版写得不好，而是**三个月后静默漂移**：文档写着 `--brand-primary`，代码已改名 `--colors-brand-primary`，没有任何东西会报错。所有"必须同步"的纪律最终都靠人自觉，而自觉不可靠——防漂移闭环就是把同步纪律变成机器检查。

### 三个可机器校验的一致性契约

| # | 契约 | 文档侧 | 代码侧 | 校验方式 |
|---|------|--------|--------|----------|
| 1 | 令牌一致 | 附录 B 的 CSS 变量全名 | `tokens.css` 中的变量名 | 两侧提取变量名 → 集合 diff，差异双向报出 |
| 2 | 组件注册表一致 | 附录 A 的导出名 | `packages/ui/src/index.ts` 的 export 清单 | 两侧提取导出名 → 集合 diff |
| 3 | 已知偏差一致 | "已知偏差"表 | issues 状态 | 每次发版前人工核对（频率最低） |

### 最小校验脚本（示意）

```bash
# validate-design-md.sh —— 挂 pre-commit / CI
# 1. 仅提取附录 B 区段的令牌定义（限定区段，避免正文示例误报）
awk '/^## 附录 B/,/^## 附录 C/' DESIGN.md \
  | grep -o -- '--[A-Za-z0-9-]*' | sort -u > /tmp/md-tokens.txt
# 2. 提取 tokens.css 中定义的变量名（去掉行尾冒号，与文档侧格式对齐）
grep -o -- '--[A-Za-z0-9-]*[[:space:]]*:' packages/tokens/dist/tokens.css \
  | sed 's/[[:space:]]*:$//' | sort -u > /tmp/css-tokens.txt
# 3. 双向 diff，非空即失败
diff /tmp/md-tokens.txt /tmp/css-tokens.txt || exit 1
```

> 使用注意：① 脚本假定附录 B 是令牌的唯一定义区段，正文示例不得混入令牌定义写法；② 路径按项目构建产物实际调整；③ 附录 A 导出名校验建议用 AST 解析（如 ts-morph）而非 grep，更稳；④ 导出名校验只针对 **✅ 可用**态组件，🔵 计划中豁免——否则零期闭环自锁。关键不在脚本多精巧，而在**挂到 pre-commit / CI**，让"只改代码没改文档"无法合入。

### 闭环时机

| 时机 | 动作 | 拦截什么 |
|------|------|----------|
| pre-commit | 跑校验脚本 | "只改了代码没改 DESIGN.md"——最常见失败模式 |
| PR 评审 | 核对三处同步（附录 A + 映射表 + 附录 B） | 语义漂移 |
| 发版前 | 人工核对已知偏差与 Open questions | 长期偏差累积 |

**原则**：本文宣称与 `tokens.css` "字符级一致"，就必须有一个能证明它的机器检查——否则它只是愿望。

## 总结

### 一句话定义

> **DESIGN.md = 一份给 Agent 看的"设计系统契约"。**
> 它用**单文件 + 9 大模块 + 4 层骨架**，把所有设计/选型/令牌/模板**集中可机读**，让 Agent 不靠预览站也能开工。

### 三大核心收益

1. **多团队协作**：所有项目/Agent 同一份文件约束，视觉一致
2. **AI 协作**：Agent 生成代码不靠预览站，直接读 SSOT
3. **变更可控**：改组件 → 改 SSOT → 跑测试，三步闭环

### 五个最重要的细节

| # | 细节 | 为什么重要 |
|---|------|-----------|
| 1 | **YAML frontmatter** | 机器可读元数据 |
| 2 | **组件选型决策规则** | 4 行定生死，约束所有 Agent |
| 3 | **组件-令牌映射表** | 改颜色时唯一可同步的地方 |
| 4 | **未实现标记 + 替代方案** | 显式禁用 + 兜底方案，防 Agent 乱引用 |
| 5 | **交付自检清单** | 验收标准明确，无歧义 |
